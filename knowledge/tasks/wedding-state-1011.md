# Wedding project state, 2026-10-11

Implemented after the user requested a project-state wedding list based on their card sketch and `/Users/cabinpxrn/Downloads/Глав док.xlsx`, sheet «Пары», headers A1:V1. Published on their subsequent explicit request as `tie-wedding-state-20261011-r1`; see [[wedding-state-release-1011]]. No workbook-row import; source workbook is unchanged.

Cards retain wedding name, date, location, phase, normal opening and date tabs/search. After the user's fourteen corrections, all eighteen active stages are plain 18px emoji buttons in two balanced rows of nine below the phase badge/property dots row. There are no frames, background boxes, folds, checks/exclamation overlays, visible captions, completion/problem counts, global legend, expanded stage section or document button. All stages remain visible without horizontal scrolling, including 320px phones. Default emoji are grayscale; completed emoji use their original colors; problem emoji have a red tint. The progress bar and percentage remain. Guests, Seating, Timing, Estimate and Tasks are excluded from both the stage list and readiness denominator. Existing stored data for retired stages remains intact.

A missing stage defaults to open without writing data. Clicking an open required stage starts an editor with done selected and focuses the comment; save commits status and comment together. A saved stage opens a small 300px anchored non-modal popover, with a pencil at the top right for editing in the same panel. There is no backdrop, blur, body scroll lock, inert background or focus trap. Outside pointer/focus and Escape dismiss; explicit close/Escape returns focus to the emoji. Unsaved form changes are discarded on dismissal. Positioning clamps to viewport sides and the visible topbar/mobile dock; limited space scrolls the popover internally. The shared `usePopover` hook accepts an optional initial focus ref, so a new/open-stage editor focuses the comment while existing notifications/account menus retain their behavior. Red requires a nonblank problem comment. «Не требуется» is an applicability flag, fades the emoji and excludes that stage from the denominator. Progress is rounded done/required; all-excluded is 0. Venue copy also reflects an explicit manual stage if the ordinary location is blank. Wedding properties save refreshes the wedding list; date editing receives that card's project ID. Core properties do not round-trip derived/private checkpoint defaults into generic mutations.

Statuses are manual organizer checkpoints. They do not select vendors, confirm booking/contracts, complete tasks, change financial rows, publish websites or modify wedding dates. No guesses are made from workbook names, prices or dash-filled cells.

`src/wedding-control.js` defines 18 active stable stage IDs and pure progress/default helpers. `project.control.save` accepts one stage and/or document/notes under optimistic project version and normal command idempotency. JSON lives in protected `project.data.weddingControl`; no schema migration/backfill. A stage update merges only that ID, preserves all other stage notes and unrelated project data, and records updater/date in the existing audit flow. Invalid status/IDs/types, >8000-character notes, unsafe/malformed/credential-bearing URLs and foreign/deleted weddings fail transactionally.

Read/edit requires organizer identity (the existing team-timing staff predicate) and current `read`/`edit` grant for project row and field `weddingControl`. `filteredProject` exposes the field and `canManageWeddingControl` only within those grants. Couple/contractor snapshots and project history redact internal comments, document links and notes, independently of finance permissions. Generic create/edit/restore cannot forge or replace the protected control field. Authorized read-only staff see the popup without editing. The action requires an online connection; ordinary offline exports/financial controls retain their previous scope. Docker runtime copies the shared module.
