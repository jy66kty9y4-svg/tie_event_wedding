# V2: интеграция модулей

Дополняет [WORKFLOW-API.md](WORKFLOW-API.md), [GUEST-API.md](GUEST-API.md) и [PUBLISHING-API.md](PUBLISHING-API.md). Фактическое покрытие описано в [VALIDATION-NOTES.md](VALIDATION-NOTES.md).

## Команды и права

Все изменения кабинета идут через `POST /api/command`: `{id, op, projectId?, ...payload}`. Нужны текущая staff session, same-origin и CSRF. `id` уникален для логической команды; повтор с другим содержимым отклоняется. `entityId`/`version` и версии родительской схемы предотвращают потерю конкурентных правок. Новые V2-команды с `offline:true` отклоняются и не включаются в клиентскую очередь.

Центральный dispatcher обновляет пользователя и проверяет текущие права **до** чтения сохранённого результата команды. Данные сущностей в результате, повторе и конфликте фильтруются по текущим правам на поля. Отдельные DTO списков также фильтруются перед сортировкой/подсчётом. Команда и уведомления фиксируются в одной SQLite-транзакции.

`guestInvite.create` и `guestInvite.rotate` показывают raw token только первоначальному вызову. В `commands.result` токена нет; в гостевых таблицах хранятся digest. Ошибка гостевого RSVP не содержит staff entity: только повторно разрешённый текущий guest context. Гость получает `{affected:[{id,version}],canRespond:true}`. Поля питания и трансфера зависят от опубликованной ревизии, а не от черновика.

## Чтение

- `GET /api/v2/workflow/tasks[/:id]`, `/approvals[/:id]`: `projectId`, фильтры и пагинация `offset/limit` (до 200). Список задач агентства собирает все доступные страницы проектов.
- `GET /api/v2/calendar/events`: проект, диапазон дат и пагинация; интервал запроса ограничен 93 днями. События содержат `actionUrl` для перехода к источнику.
- `GET /api/v2/notifications`: только доступные уведомления текущего пользователя.
- `GET /api/v2/calendar/meeting?entityId=...`: встреча после проверки текущих прав.
- `POST /api/v2/calendar/meeting-preview`: предпросмотр пересечений. Сохранение конфликта требует актуального digest и явной причины.

Сводки, готовность, настройки уведомлений и доступные участники используют выделенные маршруты в `server/http.mjs`. Ограниченные пользователи не получают полный `/api/state` в виде скрытого источника данных V2.

## Семантика тайминга

`timing.configure` принимает `projectId`, `tableId`, `schemaVersion`, `confirm` и `data:{semanticMap,createMissing}`. Карта ссылается на постоянные ID колонок:

| Поле | Тип |
|---|---|
| title | text, обязательно |
| startTime | time, обязательно |
| endTime | time |
| dayOffset / endDayOffset | number |
| required | boolean |
| assignedUserIds | users |

`createMissing` может содержать дополнительные поля dayOffset, endDayOffset, required, assignedUserIds. Изменение существующей привязки требует `confirm:true`; старый текст ответственного не превращается автоматически в аккаунт. Привязанные колонки защищены от неявного удаления/смены типа. Изменение тайминга помечает сайт dirty, сохраняя опубликованную ревизию.

## RSVP и рассадка

Сопоставление гостей требует отдельных колонок: имя/дополнительные ответы — text, RSVP — text/select с четырьмя разными значениями, стол — relation, место — number/text. Для legacy списка статусов можно явно выбрать соответствия в мастере. Полное отключение требует подтверждения, отзывает ссылки и сессии, сохраняя строки.

Общий редактор таблицы использует `guest.row.edit` для связанных полей RSVP/рассадки. Команда проверяет row/schema/table versions, вместимость, уникальность места и явное подтверждение для неподтверждённого гостя. `seating.unassign` не требует выбора нового стола. Отказ/удаление освобождают место; восстановление не возвращает занятое место.

Гостевые HTTP-маршруты `/api/public/rsvp/exchange`, `/context`, `/respond` используют отдельные cookies и CSRF, не staff session. Ответы и `/w/:shareId` имеют no-store. Гостевой JS загружается отдельным entrypoint без приватного IndexedDB-клиента.

## Миграции, публикации и офлайн

Миграции 4–6 добавляют V2-модель, очередь и аудит гостевых субъектов. Legacy public import идемпотентен по агентству и создаёт черновики. Автоматическая публикация личных данных не выполняется.

Публичные изображения проходят декодирование Sharp, ограничение размера/пикселей и пересоздание WebP без исходных metadata. Публикация создаёт отдельную разрешённую копию ресурса; приватный ID анонимно не работает. Публичные ресурсы и API не попадают в service worker; локальные `/assets/` — только статическая сборка приложения.

Внутренний outbox работает при запущенном сервере, перепроверяет текущие права и предмет события перед доставкой. Email возвращает честное состояние `not_configured`, пока внешний провайдер не подключён. Старые подготовленные офлайн-таблицы и выплаты сохраняют прежнюю синхронизацию; публичные RSVP и публикации требуют сети.
