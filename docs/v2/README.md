# tie.event v2 — пакет задания программисту

Подготовлено 8 сентября 2026 по согласованным дополнениям к tie.event и трём выбранным владельцем скриншотам WedCRM.

## Что открыть

1. **[Подробные требования](REQUIREMENTS.md)** — семь модулей, сценарии, права, поля, статусы, ограничения, порядок реализации и 47 критериев приёмки.
2. **[Расположение и дизайн](DESIGN.md)** — выбранная визуальная система, размеры, навигация, мобильное поведение, состояния и схемы экранов.
3. **[Техническое задание](TECHNICAL.md)** — источники данных, сущности, API, зависимости, миграции, время, конкурентное редактирование и правила доступа.
4. **[Интерактивный визуальный макет](prototype.html)** — восемь демонстрационных экранов. Открывается локально в браузере; внешние библиотеки и интернет не нужны.

Это пакет спецификаций, не реализация функций приложения. Макет использует вымышленные данные, не подключается к API и не сохраняет действия. Значения, сроки и статусы в реальном продукте должны вычисляться по источникам из требований.

## Выбранная компоновка

- Тёплый белый фон, белые карточки с тонкими границами, приглушённый розовый акцент.
- Постоянное левое меню организатора 240 px, верхняя панель 64 px.
- Название свадьбы и дата над горизонтальными вкладками проекта.
- Обзор агентства: четыре карточки показателей, «Требует внимания» слева, ближайшие семь дней справа.
- Проверка перед свадьбой: единый список успешных, проблемных и неизвестных пунктов с переходами в исходные записи.
- Рассадка: просторная схема с сеткой и столами; нерассаженные гости и свойства — в правой панели.
- Для телефона — доступное меню и основные переходы снизу; функции не исчезают из-за ширины экрана.

Остальные кнопки показывают пояснение будущего действия. Пример схемы не поддерживает перетаскивание/сохранение; целевое поведение полностью описано в ТЗ. В календаре показан месяц; обязательная мобильная повестка и другие виды описаны в DESIGN.md.

## Из каких сервисов взяты идеи

Функциональные описания проверялись на официальных страницах 8 сентября 2026. Закрытые кабинеты сторонних сервисов в этой задаче не тестировались. Три скриншота выше — отдельные визуальные материалы владельца.

| Источник | Полезный принцип | Применение в tie.event |
|---|---|---|
| [WedCRM](https://wedcrm.ru/) | Агентский кабинет, работа с клиентами и свадебными проектами | Главный визуальный ориентир по пользовательским скриншотам |
| [Marryo](https://marryo.ru/) | План от даты и участие пары в согласованиях | Относительные сроки задач, решения с вариантами |
| [That’s The One](https://www.thatstheone.com/) | Совместная подготовка, гости, подрядчики, расписание | Связанные разделы внутри одной свадьбы |
| [Planning.Wedding](https://planning.wedding/ru) | Гости, ответы, схема рассадки и свадебная страница | Гостевой сценарий без доступа к кабинету |
| [Aisle Planner — Client Portal](https://aisleplanner.com/products/client-portal/) | Кабинет с задачами, сроками, файлами и уведомлениями | Понятный следующий шаг для участника |

Спецификация не предполагает, что у tie.event уже есть все функции из этих источников. Например, конверсия продаж не переносится в обзор без соответствующей модели продаж; количество документов не доказывает готовность договора; число строк программы не означает корректный тайминг.

## Готовая вводная для программиста

> Реализуй развитие существующего tie.event по docs/v2/REQUIREMENTS.md, docs/v2/TECHNICAL.md и docs/v2/DESIGN.md. Начни с knowledge/INDEX.md, актуальных исходников и проверки текущих незакоммиченных изменений. Сохрани существующие заявки, аккаунты, гибкие таблицы, финансовый журнал, права, историю и офлайн-сценарии. Новые модули должны использовать текущие гости/подрядчики/обязательства, а не создавать параллельные копии.
>
> Основной дизайн — приложенные WedCRM-референсы: постоянное левое меню, верхняя панель, вкладки внутри свадьбы, белые карточки и приглушённый розовый акцент. Макет docs/v2/prototype.html показывает компоновку, но не заменяет функциональную реализацию. Внешний вид адаптировать к tie, сохраняя доступность и полный начальный доступ пары к её проекту.
>
> Реализуй все семь модулей в указанной последовательности, согласуй центральные DTO/миграции перед параллельными изменениями. Закрой AC-01…47, а также прежние регрессии. Сдай исходники, миграции, обновлённый API-контракт, результаты проверок и инструкцию запуска. Покажи реальные сохранение, повторный вход, конфликт двух сессий и гостевой доступ. Рабочую БД не заменяй демоданными. Не меняй другие продукты и не публикуй вымышленные кейсы/цены как реальные.

## Материалы для заполнения перед публичным выпуском

Разработку и локальную приёмку можно выполнить на нейтральных образцах. Для публичного выпуска владелец заполняет название/контакты агентства, фотографии и тексты реальных кейсов, состав/стоимость услуг, ответы FAQ и окончательный домен. Если подключается email, отдельно настраивается действующий провайдер. Отсутствие этих материалов не должно порождать выдуманные публикации или ложное сообщение об отправке.
