## HTTP API (runtime worker owns)

GET /api/public?agency=tie → publicInfo; POST /api/setup → bootstrap only when DB empty, POST /api/register, /api/login → register/authenticate sets session cookie. POST /api/logout clears server session. GET /api/state?project=ID → snapshot. GET /api/offline?project=ID → snapshot(...,true). POST /api/command → execute. POST /api/files?project=ID → upload JSON base64. GET /api/files/ID → authorized download. GET /api/health. Server imports db/auth/service. Errors `{error,details}`, status from Fault, no raw stack. All mutation requests same-origin JSON, rate limiting, 12 MB request ceiling. Serve dist shell for SPA routes. Static service worker MUST NOT cache API/private network responses.

State shape: `{user,agency,grants,onboarding,projects,applications,accountRegistrations?,notifications,global,roles,users,assignments,financials}`. `loadState(project)` returns `{user,agency,grants,project,entities,members,history,financials}`; `history` is returned only when the user has the `history` permission for that project. Entity `{id,agency_id,project_id,kind,parent_id,data,version,deleted,updated_at}`. Project files use `{name,size,mime,documentStatus:'personal'|'pending_signature'|'signed'}`. Tables data `{name,key,sectionId,order,archived,offline,columns:[{id,name,type,options?,formula?}]}`. Rows have parent_id table ID, data is column ID/value map. Both timing views use one `key:timing` table, seating uses `key:guests`.

Account entry: `/api/register` requires both `email` and `phone` plus the existing name/password/agency fields. Registration rejects a missing contact, malformed/overlong number or non-Russian phone with 400; the phone must normalize to exactly `+7` and ten national digits. Russian ten-digit numbers and domestic `8` input normalize to `+7…`. `/api/setup` retains its compatibility with either identifier. Existing email-only and phone-only accounts remain valid; phone-only users have `email: null` and a canonical `phone`, and legacy international phones remain supported by authentication. Uniqueness remains scoped to the agency. `/api/login` accepts `{identifier,password,slug?,rememberSession?}`; legacy `email` and explicit `phone` request fields also work. Login requires the password in the same request. `rememberSession: false` omits cookie persistence; omitted/true retains seven days. Email-bound invitations still require their matching email, including when registration also supplies a phone number. Public registration does not grant project or staff access. New public/couple-invited accounts get `onboarding:{id,version,userId,status:'pending'|'questionnaire'|'complete',projectId,project:{id,version,name,date}|null,approvedBy,approvedAt,questionnaire,questionnaireSubmittedAt}`. Administrator approval uses an existing wedding; only the completed questionnaire opens the wedding workspace. `accountOnboarding` is a protected global entity kind, excluded from generic entity mutation. Before completion, grants/private wedding snapshots, offline preparation and other commands are denied; only the owning account may submit its questionnaire after approval. Existing accounts without an onboarding entity and employee invitations retain their prior access. Manageable entries in the administrator's `users` list include onboarding stage and submitted answers.

Registration inbox: global snapshots for users with `applications` or `access` permission include `accountRegistrations` (flattened onboarding entries plus public `user` contacts and `canApprove`). Active accounts in the same agency only; completed entries retain their questionnaire for the processed tab. Other users receive no field. Existing `applications` records remain separate. Signup transactionally queues `account.registered` to active reviewers/access administrators and immediately processes only that source; the durable worker retries failures. Notifications use the title «Новая заявка на регистрацию» and `/app/applications?registration=ID`. Visibility rechecks current review rights and active source account. `server/backfill-account-registrations.mjs` restores notifications for existing pending accounts idempotently, without approving or changing accounts, grants or weddings.

## Frontend client module (runtime worker owns src/client.js)

`api(path, options?)` JSON fetch with same-origin credentials, throws Error with `.status` and `.details`.

`loadState(projectId = null)` server snapshot online, prepared snapshot offline. `command(body)` adds crypto.randomUUID id when absent, sends online; queues only row edits and movement.save in prepared project offline, returns `{queued:true,id}`. On successful queued mutation update local snapshot. Never queue non-network server errors. `prepareProject(projectId)` explicitly fetches permitted configured offline snapshot, saves into IndexedDB. `getOfflineStatus(projectId?)` → `{preparedAt,expiresAt,pending,conflicts,projects:[{id,name}]}`; pending count, conflicts array `{id,command,error,status,details}`. `syncQueue()` sequential authorized replay, keep failed commands for user decisions. `discardCommand(id)` removes a failed command only on user click; `retryCommand(id, replacements)` explicitly changes versions/schema versions after user review (new id when changing content). `logout()` clears private storage and server session (offline logout clears locally, next online session cannot restore old identity). `subscribe(callback)` returns unsubscribe for window online/offline/client data event; `initClient()` registers SW and checks/sanitizes identity on online account switch. Use plain event/callback API, UI owns React state. Exports must exist.

## Commands (server worker owns domain)

All `{id,op,projectId?}`. Mutations return entity/result; UI reloads afterward.

- project.create `{data:{name,date?,location?,limit?},templateId?}`; an omitted or empty date means an open wedding date.
- account.approve `{entityId,version,weddingId}` requires agency access administration and permission to assign the couple role. Confirms an active pending account and assigns an existing same-agency wedding atomically; status becomes `questionnaire`. A pre-submission reassignment increments version and replaces the assigned wedding. No new wedding is created.
- account.questionnaire `{entityId,version,answers}` only the owning account, after approval; validates all 33 existing questionnaire prompts and assigned wedding availability, stores the answers and sets `complete`. Missing/invalid answers leave access closed. Registration already collected contacts and the administrator selected the date, so this questionnaire does not request contacts/date again.
- application.create `{data:{name,date,contact,message}}` legacy registered user; application.review `{entityId,version,status,reason}`
- invite.create `{projectId,email,roleId,restrictions?}` returns token; invite.accept `{token}`
- invite.revoke `{invitationId}`; creation returns `{id,token,email,expiresAt}` and defaults to the couple role when roleId is omitted. Acceptance rechecks the issuer's current authority.
- application.respond `{entityId,version,data:{name,date,contact,message}}` lets the applicant resubmit after clarification/rejection.
- role.save `{roleId?,version?,name,permissions:[...]}`; role.delete `{roleId,version}` удаляет только пользовательскую роль без назначений и приглашений; grants.save `{userId,version,disabled,grants:[{roleId,projectId,restrictions:{sections,rows,fields}}]}`
- settings.save `{version,name,settings:{tagline,description,contact,services:[string],portfolio:[{title,image,description?}]}}`
- entity.create `{projectId?,kind,parentId?,data,schemaVersion?}`; entity.edit `{projectId?,entityId,version,data,schemaVersion?}` patches fields; entity.delete `{projectId?,entityId,version,schemaVersion?,confirm?}` soft delete with reference warning; entity.restore `{...,auditId?}`
- movement.save `{projectId?,entityId?,version?,obligationVersion?,data:{type,amount,date,description,source:'custody'|'direct',from?,to?,obligationId?,categoryId?,fileId?}}`; movement.delete `{projectId?,entityId,version}`. Money is integer kopecks. Types deposit, payment, refund, transfer, fee (wedding), income/expense (agency).
- coupleBudget.cell `{projectId,row,field,value,format?}` saves a sparse estimate value and optional formatting atomically. Text fields are `name`/`note`; amounts `estimated`/`actual`/`prepaid` remain integer kopecks or null; `organizer` remains boolean. `coupleBudget.format` `{projectId,row,field,format,value?}` changes presentation only, including calculated `remaining`. Both require combined edit/finance permission for that exact budget field and row. For text formatting, an optional `value` must match current text or returns 409. `format: null` removes formatting. Omitted format on legacy text edits rebases existing ranges.
- `sheet.layout` `{projectId,entityId?,axis,key,value}` merges one persistent dimension: `columnWidths` 80–800 px or `rowHeights` 32–500 px. A table ID selects a generic table; omission selects the couple estimate. Unknown IDs are rejected. Requires edit/structure and, for the estimate, finance.
- Generic row `entity.edit` accepts separate `formats:{[columnId]:format|null}`, `formatOnly?`, `expectedValue?`; exact field grants and current row/schema versions apply. Direct raw `data.cellFormats` is rejected. Text edits rebase prior ranges. Table/row layouts and values preserve stable IDs; removed generic columns/rows remain recoverable through history.
- `coupleBudget.structure` `{projectId,action:'columns',columns,hiddenColumns}` stores ordered definitions, labels, visibility and typed custom columns; financial base IDs/types/formulas remain protected. Removed custom definitions are archived; values/styles remain. `action:'delete'|'restore',row` uses string tombstones for an item/section; restore additionally requires history and retains original values/styles/dimensions. Structure requires edit/structure/finance; deletion requires delete/finance. Extra fields in cell/format commands use the declared type. `extraValues[columnId][row]` holds typed custom metadata independently of cash.
- `financeSheet.cell` `{projectId:null|uuid,target?:'obligation',entityId,version,field,value,format?,formatOnly?,expectedValue?}` edits a journal/obligation cell. It requires combined edit/finance (project) or edit/agencyFinance (agency) for that exact row/field. Base edits use existing financial/reference/ledger validation; paid/due/formula values are immutable. Custom values use `sheetValues[field]`; formatting uses `cellFormats[field]`. `movement.save` and general obligation mutation reject raw custom/style metadata. Commission retains organizer-only access. No custom field creates a cash movement.
- `financeSheet.structure` `{projectId, target?, columns, hiddenColumns}` requires edit/structure plus finance/agencyFinance; financial base IDs/types are retained, custom definitions can be removed/restored. `financeSheet.layout` `{projectId,target?,axis,key,value}` applies the same dimension limits. A financeSheet entity stores project journal/obligation or agency journal presentation; no migration is required.
- `movement.restore` `{projectId,entityId,version,obligationVersion?}` restores a soft-deleted operation once using current financial/reference/funds validation; requires edit/history and finance/agencyFinance. Snapshot `deletedFinanceRows` contains only broadly authorized deleted operations/obligations. Restoring does not create a duplicate operation.
- Authenticated `GET /api/export.xlsx?project=<uuid>&kind=table|budget|financeSheet|seating&table=<uuid>&audience=Пара|Команда` or `kind=agencyFinance&project=` sends real XLSX bytes with UTF-8 Content-Disposition and private/no-store. Same read/finance/agencyFinance/table scopes as snapshot apply. Workbooks retain typed numbers/dates/times, dimensions/order/styles, custom columns and recalculating formulas with cached values. Selects use hidden named-range lists; text starting '=' remains literal. Partial-run background highlights become a whole-cell fill in native Excel; partial font formatting is preserved. Browser offline fallback still builds XLSX from authorized cached state.

Estimate presentation is stored in `coupleBudget.data.cellFormats[field][row]` as `{style:{bold?,italic?,fontSize?,color?,highlight?},ranges:[{from,to,style}]}`. Text offsets are UTF-16, bounded by the plain text; overlapping ranges normalize. Font sizes are 12/14/16/18/20/24/28, colors are six-digit hexadecimal, and highlight also permits `none`. Projection uses filtered field-authorized source rows. No movements are created from estimate cells: the displayed fee advances follow the estimate, while `financials.income/own` and the UI's «Касса по операциям» retain the actual movement ledger. ### Contractor profiles (2026-10-11)

## Wedding organizer checkpoints (local, 2026-10-11)

`project.control.save` takes `projectId`, current project `version` and either/both `stage: {id, status, comment, notRequired}` / `info: {documentUrl, notes}`. Stage IDs are the 18 active definitions in `src/wedding-control.js`; retired Guests, Seating, Timing, Estimate and Tasks IDs cannot be newly edited and no longer count toward readiness, while their historical JSON is preserved; statuses are only `open`, `done`, `problem`. `notRequired` must be boolean; true normalizes status to open and excludes the stage from progress. Problem comments must be nonblank; comments/notes are capped at 8000 characters. Document URL is blank or a valid HTTP(S) URL without embedded credentials, max 2000 characters. The update preserves unrelated project data and other stages. Standard audit, command idempotency and 409 optimistic conflict handling apply. No migration or financial/vendor/task side effects.

The caller needs the existing organizer identity predicate plus current `read` and `edit` grant on the project row and `weddingControl` field. Snapshots return that field only to authorized staff, with `canManageWeddingControl`; nonstaff and denied fields are redacted in project history independently of finance permissions. Generic project mutations cannot replace the protected field. This organizer workflow requires a connection and is not queued offline.


## Automatic wedding templates (2026-10-12)

`project.template.create` takes the ordinary unique command `id`, `projectId`, current `projectVersion`, and template `name`. The server captures current allowed reusable definitions transactionally, requires organizer authority, wedding read+structure and agency create+templates rights, and checks source read scopes. It returns a new global `template` entity and does not mutate the source project. Repeat IDs use ordinary authorization-before-replay rules. Foreign/deleted/unavailable weddings and stale versions fail without partial data. Capture requires a connection.

The template retains sections, table schemas/formulas/options/mappings/offline flags/shared widths; budget articles/structure/labels/organizer flags/visibility/sizes/cell styles; payout schemas with protected computed fields, visibility and widths; task titles/phases/dependencies/priority with relative or no deadlines; project timezone/readiness policy; unassigned hall geometry; website design/block/RSVP feature settings. It excludes filled rows/financial values/payment records/notes/guests/vendors/files/meetings/approvals/actors/public content and tokens. New project IDs/bindings are independent. `project.create` uses template blueprints and resets status/assignees/links/amounts. Enabling invitations still requires the administrator settings grant. Ordinary template edits retain extension data and revalidate it. See `tests/wedding-template.test.mjs` for invariant and access checks.
