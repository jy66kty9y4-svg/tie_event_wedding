# Интеграция календарей

Для шифрования OAuth-токенов и паролей приложения серверу нужен постоянный секрет длиной не менее 32 символов:

- `TIE_CALENDAR_SECRET`

Google Calendar дополнительно требует:

- `TIE_PUBLIC_ORIGIN` — публичный адрес приложения, например `https://tie-event.example`;
- `GOOGLE_CALENDAR_CLIENT_ID`;
- `GOOGLE_CALENDAR_CLIENT_SECRET`.

В Google Cloud нужно включить Google Calendar API и добавить разрешённый redirect URI:

`<TIE_PUBLIC_ORIGIN>/api/v2/calendar/google/callback`

После подключения сервер регистрирует отдельный Google push-канал на HTTPS webhook:

`<TIE_PUBLIC_ORIGIN>/api/v2/calendar/google/webhook`

Добавлять webhook в OAuth-клиент не требуется. Канал подтверждается случайным секретом, сохранённым только как SHA-256, автоматически продлевается до истечения и удаляется при отключении календаря.

Для Apple пользователь вводит Apple Account и отдельный пароль приложения в интерфейсе. Основной пароль Apple использовать нельзя. Сервер автоматически находит iCloud CalDAV и создаёт отдельный календарь свадьбы.

Для каждой свадьбы и пользователя создаётся отдельное подключение. Изменение задачи или встречи на сайте сразу ставит синхронизацию подключённых календарей в очередь. Встречи передаются с точным временем, часовым поясом, местом и заметкой; встречи календаря агентства без свадьбы входят в организаторский календарь. Google сообщает об изменениях push-уведомлением, после которого сервер забирает дельту по sync token; открытый календарь сайта обновляется автоматически. Минутный фоновый цикл остаётся резервом и обслуживает Apple Calendar, где аналогичного push-механизма нет. Кнопка «Проверить сейчас» нужна только для диагностики. Завершённые, отменённые и задачи без срока удаляются из внешнего календаря. Конфликт одновременных изменений разрешается в пользу изменения на сайте.

В организаторском календаре внешнее событие на весь день без префикса свадьбы импортируется как событие агентства на весь день. Если название начинается с точного префикса `Название свадьбы — `, событие на весь день маршрутизируется как задача этой свадьбы.

Удаление идемпотентно: если пользователь успел удалить одно событие и на сайте, и во внешнем календаре, ответы внешнего сервиса 404/410 считаются успешным подтверждением удаления. Старая связь очищается и не блокирует синхронизацию остальных событий.

Задачи с периодом используют включительные начало и окончание на сайте; в Google/Apple
передаётся событие на весь день с исключительным окончанием на следующий день после
последнего дня периода. Несколько дней внешнего события импортируются как период;
существующий однодневный период сохраняет свой режим. `dueDate` задачи равен последнему
дню периода. Задачи без срока остаются в плане; снятие даты удаляет связанную запись из
подключённого календаря. Проверка round trip выполнена с mock Google, без обращения к
личным календарям пользователей.

## Восстановление и расположение управления (12 октября 2026)

Кнопка «Синхронизация календарей» находится в заголовке календаря; из настроек/профиля удалена. В календаре агентства по умолчанию выбрано agency, в проектном — свадьба. Подключения, OAuth и провайдеры не менялись.

`meeting.restore` принимает projectId (null для агентства), entityId, актуальную version и необязательный auditId. Без auditId допускается только удалённая встреча; с ним берётся предыдущая версия из истории той же agency/entity/kind/project. Read/edit/history и изменяемые поля проверяются вместе; участники/время/привязка к свадьбе валидируются по текущему состоянию. Пересечение возвращает409 с conflicts/digest; повторный запрос требует свежий conflictDigest и conflictReason. Причина исключена из digest как подтверждающее поле, геометрия времени/участники/конфликты остаются связанными. UI при устаревшем пересечении обновляет список/digest для повторного подтверждения. Команда входит в автоматическую очередь Google/Apple.
